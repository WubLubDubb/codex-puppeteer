# 初始化项目规范

## 1. 目标

基于一个从 GitHub clone 下来的起始仓库补齐项目工作骨架，使仓库从“仅包含规则与入口文档”进入“可继续进行需求、设计、开发和测试”的状态。

## 2. 可参考输入

- 当前工作目录
- 用户对项目目标、技术栈或远程仓库策略的说明
- 当前仓库的现有内容与 Git 状态
- 起始仓库是否仅包含 `README.md`、`AGENTS.md`、`agent-specs/`

## 3. 初始化前提

- 当前目录默认已经是一个从 GitHub clone 下来的项目仓库。
- 起始仓库的最小内容默认为 `README.md`、`AGENTS.md`、`agent-specs/`。
- 初始化阶段的主要任务是在此基础上补齐 `docs/`、`.agent/`、`src/`、`tests/` 等工作目录与基础文档。
- 若仓库已经存在部分项目骨架，应在保留现有内容的前提下补齐缺失项，而不是盲目重建。

## 4. 输出

- 保留并更新已有的 `README.md`
- 保留并更新已有的 `AGENTS.md`
- 保留并更新已有的 `agent-specs/`
- 新增或补齐 `docs/`
- 新增或补齐 `.agent/`
- 新增或补齐 `src/`
- 新增或补齐 `tests/`
- 如有需要，补充 `.gitignore`
- 在现有 Git 仓库基础上形成可继续推进的项目初始化结果

## 5. 执行步骤

1. 检查当前仓库是否已经包含起始内容以及现有项目骨架。
2. 基于现有结构补齐缺失目录和基础文件，不覆盖用户已存在的有效内容。
3. 按各规则中的最低结构初始化基础文档。
4. 创建或补齐 `.agent/state.md`、`.agent/current-state.md`、`.agent/traceability.md`。
5. 校验当前 Git 仓库状态、远程配置和后续可用性，但不把重新 `git init` 当成默认动作。
6. 如用户要求且远程与权限条件允许，再进行提交或推送。

## 6. 必做检查

- `README.md` 必须存在。
- `AGENTS.md` 必须存在。
- `agent-specs/` 必须存在。
- `docs/` 下至少存在需求、设计、计划、验收、开发日志索引文档。
- `.agent/state.md` 中必须记录当前阶段。
- 当前目录必须保留有效 Git 仓库状态；如果是 clone 下来的仓库，不应错误地当成未初始化项目。

## 7. 基础文档最低要求

- `README.md` 至少说明项目简介、当前目录结构和当前状态。
- `docs/requirements.md`、`docs/system-design.md`、`docs/development-plan.md`、`docs/acceptance-report.md` 的初始化内容，应至少满足对应规则中的最低结构，允许先写占位说明，但要明确当前不完整。
- `docs/change-log.md` 应作为开发日志索引入口。
- `.agent/current-state.md` 应说明当前阶段、阻塞和下一步建议。

## 8. Git 约束

- 如果当前项目是从 GitHub clone 下来的仓库，应默认沿用现有 Git 仓库，而不是重新初始化。
- 只有在当前目录缺失 Git 仓库且用户目标明确要求独立建仓时，才执行新的 Git 初始化。
- 若检测到父目录已经是 Git 仓库，但当前 clone 仓库本身已具备独立 `.git`，不得误判为需要重新建仓。
- 若远程、权限或策略导致无法推送，必须保留本地产物并报告阻塞原因。

## 9. 停止条件

- 当前目录既不像起始仓库，也缺少足够上下文，无法判断应补齐还是应重建。
- 现有仓库结构与规则假设严重冲突，继续初始化会覆盖用户现有项目。
- Git 状态异常到无法确认当前仓库边界。

## 10. 完成定义

当且仅当起始仓库入口文件仍被保留，项目工作骨架与基础文档已补齐，状态文件已建立，并且当前 Git 仓库状态可继续支撑后续阶段时，初始化阶段才算完成。
