# Git 操作规范

## 1. 目标

在不破坏工作区和不误导项目状态的前提下，完成阶段性提交与可选推送。

## 2. 何时参考本规范

- 初始化项目完成后的首个提交。
- 需求、设计、开发、测试阶段完成后的阶段提交。
- 用户显式要求推送远程仓库。

## 3. 仓库边界规则

- 当前目录默认是独立项目仓库。
- 如果父目录已经是 Git 仓库，当前目录仍可初始化为独立仓库。
- 检测到父目录是 Git 仓库时，应记录“当前项目为独立仓库，允许嵌套于父目录树中”，但不应因此中止初始化。
- 不得因为父目录存在 Git 仓库就跳过当前目录的 Git 初始化。
- 如果当前目录尚未完成独立 Git 初始化，不得宣称初始化阶段已经完成。

## 4. 提交规则

- 提交前必须确保阶段产物已落盘。
- 提交信息必须体现阶段与内容。
- 若存在未完成的关键阻塞，不应伪装为完整提交。

推荐提交信息格式：

- `chore(init): bootstrap project workflow`
- `docs(requirements): add initial requirements`
- `docs(design): add system design`
- `feat(core): implement first milestone`
- `test(acceptance): record validation results`

## 5. 推送规则

- 只有在远程配置存在且认证可用时才执行推送。
- 推送失败时必须保留本地提交。
- 提交或推送动作完成后，应记录到当日 `docs/dev-logs/<YYYY>/<YYYY-MM-DD>.md`，并同步更新 `docs/change-log.md` 中的最近完成内容。

## 6. 版本号规则

- 项目版本号默认采用语义化版本格式：`vMAJOR.MINOR.PATCH`，例如 `v1.2.3`。
- 发生不兼容变更或需要显式声明重大升级时，递增 `MAJOR`。
- 新增向后兼容的功能时，递增 `MINOR`。
- 修复缺陷、补充文档、微调实现且不引入新功能时，递增 `PATCH`。
- 若只是阶段性提交而非可对外说明的版本发布，不强制创建新版本号。
- 若执行版本发布、版本切换或打标签，应优先使用 Git tag，并保持版本号与发布说明一致。
- 若本次 Git 操作涉及版本号变更，应在提交说明、`docs/change-log.md` 和当日日志中明确记录版本号及变更原因。

## 7. 同步原则

- Git 操作不单独代表阶段完成，只有相关文档、代码和状态都落盘后，提交记录才有意义。
- 若提交或推送涉及关键版本切换、验收结论或发布动作，应同步更新 `.agent/current-state.md`。

## 8. 禁止事项

- 不得为了整洁而丢弃用户未授权的修改。
- 不得伪造已推送状态。
- 不得跳过文档更新直接提交代码阶段成果。
